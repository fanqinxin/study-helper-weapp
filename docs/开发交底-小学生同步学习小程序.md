## 一、技术方案（已确认）

| 层面 | 选型 | 说明 |
|---|---|---|
| 前端 | **原生微信小程序** | 只做微信端，性能与微信能力支持最优 |
| 后端 | **自有服务器 + Node.js** | AI 中转、额度闸门、业务逻辑全部自主可控 |
| 数据库 | MySQL 8（或 PostgreSQL） | 关系型，教材/课文/错题有明确关联 |
| AI | **模型可配置** | 通过配置层切换服务商，代码不绑定具体模型 |
| 缓存/队列 | Redis | 额度计数、批改任务状态、幂等去重 |

**部署形态建议**：单台 4C8G 云服务器起步即可。Node 服务用 PM2 守护，Nginx 反代 + HTTPS，域名需完成 ICP 备案（小程序 request 合法域名强制要求）。

### 3.5 数据库访问约定（踩过坑，必须遵守）

项目有两个查询入口，**返回结构不同**，混用只会在运行时炸，语法检查完全看不见：

| 入口 | 返回 | 正确写法 | 错误写法（会炸） |
| --- | --- | --- | --- |
| `db.query(sql, params)` | 行数组（`[{...}]`）；INSERT/UPDATE 返回 OkPacket | `const rows = await db.query(...)` | `const [rows] = await db.query(...)` → `rows` 变成第一行，`rows.length` 为 `undefined` |
| `conn.query(sql, params)` | `[rows, fields]`（原生 mysql2，事务回调里的 `conn`） | `const [rows] = await conn.query(...)` | `const rows = await conn.query(...)` → `rows[0]` 是字段描述，`res.insertId` 取不到 |

**要单行怎么办**：`const rows = await db.query(...); const one = rows[0] || {};`

**不要写的函数签名**：`async function f(uid, conn = db)` —— 一个函数同时兼容两种入口，必然在某一侧解构错。若确实要双入口，在函数内部抹平（参考 `quota.ensureAccount` 的 `select` / `runOn` 写法），**且所有写入必须走这个适配器**，不能在双入口函数里裸写 `conn.query(...)` —— `conn` 为 `null` 时会抛 `Cannot read properties of null (reading 'query')`（余额接口就这么 500 过）。

**DATE / DATETIME 列**：mysql2 默认把 `DATE` 解析成 JS `Date`（受连接 `timezone: '+08:00'` 影响）。所以

- 不要用 `acc.cycle_start !== '2026-10-26'` 比较 —— `Date` 与字符串永不相等，逻辑会静默走错分支（quota 曾因此每个请求都重置免费额度）
- 不要把 DATE 列直接 `AS` 别名返回给前端 —— JSON 化后是 `2026-10-25T16:00:00.000Z`，日期差一天
- 统一做法：SQL 侧 `DATE_FORMAT(plan_date, '%Y-%m-%d') AS planDate`，JS 侧比较前先归一化成 `YYYY-MM-DD`

`npm run check` 会依次跑 `check-requires.js`（引用/依赖）、`check-query-usage.js`（上述写法）、`selftest-quota.js`（额度服务假 DB 自测）。

## 四、后端接口设计

统一前缀 `/api/v1`，统一响应体：

```json
{ "code": 0, "msg": "ok", "data": {} }
```
`code` 非 0 为业务错误。**额度不足固定用 `code: 4010`**，前端据此唤起拦截弹层。

|---|---|---|
| POST | `/homework/upload` | 上传图片（**先传对象存储，再提交**） |

| GET | `/homework/:id/report` | 获取完整报告 |

**`/homework/analyze` 的关键逻辑（必须严格按序）：**

```
1. 校验额度（免费剩余 or 付费余额）—— 不足直接返回 code 4010
2. 检查 image_hash 幂等 —— 已批改过则直接返回原结果，不扣额度
3. 原子扣减额度（Redis Lua 脚本保证并发安全）
4. 写 quota_log 流水
5. 创建 homework 记录（status=1 批改中）
6. 投递到批改队列，立即返回 homework_id

—— 批改失败时：回滚额度 + 写退款流水 + status=3
```

**额度扣减必须放在任务投递之前**，绝不能等批改成功再扣——否则并发请求会超发。

## 五、AI 批改服务层（模型可配置）

这是整个项目最需要设计好的部分。核心原则：**业务代码不感知具体模型**。

### 5.1 目录结构

```
src/ai/
├── index.js              # 对外统一入口：recognize() / judge()
├── provider/
│   ├── base.js           # 抽象基类，定义接口契约
│   ├── qwen.js           # 通义千问实现
│   ├── hunyuan.js        # 腾讯混元实现
│   └── openai.js         # OpenAI 兼容协议实现
└── config.js             # 从环境变量读取，决定用哪个 provider
```

### 5.2 配置方式

`.env`：

```bash

# 识别与判题可分别指定不同模型，控制成本

AI_VISION_MODEL=qwen3.7-plus       # 手写作业识别

AI_API_KEY=sk-xxxxxxxx

# 批改相关参数
AI_MAX_RETRY=2
AI_TIMEOUT_MS=60000
```

### 5.3 关键实现要点

**两步走，不要一步到位：**

```js
// 第一步：多模态识别 —— 图片 → 结构化题目
async function recognize(imageUrls, subject) {
  const prompt = `请识别图片中的${subjectName}作业，逐题输出 JSON 数组：
    [{ "seq": 1, "stem": "题干", "student_ans": "学生写的答案" }]
    只输出 JSON，不要解释。`;
  return callVisionModel(imageUrls, prompt);
}

// 第二步：文本判题 —— 题目 + 标准答案 → 对错与解析
async function judge(questions, lessonContext) {
  const prompt = `你是小学${subjectName}老师。根据课文《${lessonContext.title}》
    判断下列各题对错，输出 JSON：[{ "seq":1, "is_correct":true, "correct_ans":"", "analysis":"讲解" }]`;
  return callTextModel(questions, prompt);
}
```

**为什么要分两步**：直接让多模态模型判手写作业准确率差（手写体识别 + 判题混在一起，错误会被放大）。分开后：识别可以重试，判题可以用更便宜的文本模型，成本也更可控。

**必须做的工程处理：**

1. **图片预处理**：前端压到 1MB 以内、最长边 1600px 再上传。这一步能省 60% 以上成本。
2. **强约束输出格式**：prompt 里明确要求纯 JSON，代码里做容错解析（去掉 ```json 包裹）。
3. **失败降级**：模型返回不可解析时重试 2 次，仍失败则标记 `status=3` 并**退还额度**。
4. **记录原始返回**：`homework.raw_result` 存模型原始响应，这是后续调优 prompt 的唯一依据。
5. **超时与并发**：单次批改 60s 超时；同一用户并发批改数限制为 1。

### 5.4 成本估算（务必心里有数）

单次批改约消耗 1 张图（视觉模型）+ 1 次文本判题：

| 项 | 估算 |
|---|---|
| 视觉识别 | 约 1500-2500 input tokens |
| 文本判题 | 约 800-1500 tokens |
| **单次成本** | 约 ¥0.02 - ¥0.06（视模型而定） |

按免费额度每周 20 次算，**单用户每月的免费成本约 ¥0.8 - ¥2.4**。加油包 ¥12/100 次（¥0.12/次）有足够毛利缓冲。设计稿里的定价是按这个测算定的。

## 七、必须提前处理的合规与技术风险

### 7.1 合规（教育类小程序尤其严格）

| 事项 | 说明 | 时间成本 |
|---|---|---|
| 主体认证 | 个人主体**无法**开通支付和部分能力，建议企业主体 | 1-2 周 |
| 类目审核 | 教育类目可能需要资质证明 | 视情况 |
| 微信支付 | 需企业主体 + 商户号，个人不可申请 | 2-4 周 |
| 隐私协议 | 收集未成年人信息，需家长同意条款 | 必须 |
| ICP 备案 | 服务器域名备案，否则无法在小程序请求 | 2-3 周 |

**建议**：备案和主体认证**立刻启动**，它们是最长的关键路径，别等代码写完才办。

### 7.2 支付与数据安全（上线前必须完成）

| 事项 | 要求 |
|---|---|
| 支付回调验签 | `/order/notify` 必须验签 + 校验金额 + 幂等（同一 `wx_trade_no` 只入账一次） |
| 订单号生成 | 全局唯一，建议 `时间戳 + 用户ID + 随机位`，禁止自增 |
| 额度入账时机 | **只认服务端回调**，绝不信任前端支付成功回调 |
| 对账机制 | 每日跑一次 `order` 与微信账单比对，异常告警 |
| 用户数据删除 | 提供注销入口，级联删除作业图片与批改记录（未成年人数据合规） |
| 数据库备份 | 每日全量 + binlog，保留 30 天。教育类用户数据不可丢 |
| 接口限流 | 登录、批改、订单创建三处必须限流，防刷 |

### 7.3 技术风险

1. **手写识别准确率** — 最大不确定性。建议 Phase 2 一开始就先做小样本验证（拍 20 张真实作业跑识别），别等全做完才发现效果不行。
2. **AI 调用超时** — 必须异步 + 轮询，不能同步等待。设计稿的「AI 批改中」页面就是为此准备的。
3. **额度超发** — 必须用 Redis 原子操作 + 唯一索引双保险。
4. **图片存储成本** — 存储比 AI 调用更容易失控。建议原图保留 30 天，批改后只留缩略图。

### 7.4 一个务实的建议

**别一次做完 21 屏**。Phase 2 结束后就应该找 3-5 个真实家长试用，拿到两个关键数据：

- AI 批改的**实际准确率**是否可接受
- 免费 20 次/周是否**够用**（不够就得调，这是定价基础）

这两个数据会直接影响 Phase 3 要不要做、怎么做。

## 九、开工清单（第一周要做的具体事）

1. 注册小程序账号，提交主体认证 → **立即启动，最长路径**

第 7 项最重要——它是整个产品能否成立的前提。
